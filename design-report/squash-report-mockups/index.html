What the loaded screen tells us

The existing page was inspected without reload, navigation, filter changes, or server requests from the report UI. Its populated results were not inspected because no iteration was selected.

  • Selection is the main friction. The loaded selector exposes 379 readable iterations, including repeated labels and archived folders. A single long dropdown makes the correct hierarchy hard to recognize.
  • The empty state creates an unnecessary dependency. “Pick an iteration, then Save filter” mixes generating a report with saving a preference. Display results after selection and Apply; saving is optional.
  • The dates are ambiguous. Numeric day/month order is hard to infer. Keep date pickers, but summarize the applied range as “10 Aug – 8 Sep 2026” and expose timezone and inclusive boundaries.
  • “Uptime” promises more than execution data proves. The current subtitle says one bar per automated suite. Equal-width run bars encode execution sequence, not elapsed time or actual service availability.
  • Navigation needs a stable report identity. The screen has Reporting and DTN Reports alongside each other. Keep the plugin under DTN Reports → Iteration reports, with Automated suites and Status board as views.

The GitHub Status reference uses a headline status, component histories, a legend and incident history. Adapt that hierarchy; use test-outcome language and recent execution exceptions instead of claiming confirmed service incidents.

Data and interaction contract

  • Entity: one table row = one automated suite run, containing multiple test executions. Verify your Squash version’s available fields and aggregate-status mapping before implementation.
  • Two rates: table run success = passed / (passed + failed + error) suite runs. Board passed-day rate = all-passed days / days with completed outcomes. Always show the denominator; these rates intentionally differ.
  • Incomplete outcomes: running, cancelled, not-run, blocked and unknown must remain distinct in detailed data. Do not silently convert them to failure or success. The prototype demonstrates passed, failed, execution error, cancelled and missing-run states.
  • Daily precedence proposal: error → failed → running → passed. A day with only cancelled/skipped/not-run outcomes has no completed outcome; it must be distinguishable from a day containing no suite records. Confirm precedence with the customer.
  • Freshness: latest check needs a timestamp. “Missing” requires a configured expected schedule plus grace interval; ad hoc iterations should say “Last run…” rather than overdue. A stale last pass should never appear current.
  • Time: filter by suite start time in the selected timezone; include both boundary dates. In production, convert to a half-open timestamp interval ending at the next local midnight. Explain runs spanning midnight.
  • Scale: server-side search and pagination for the table; daily aggregation on the server for long histories. Keep filters, sorting and pagination in the URL. Export all matching rows, not only the loaded page.
  • Access: enforce existing Squash permissions in both report and export. Project selection should use the same access scope as the host application.
  • Accessibility: text and icons accompany color; history bars support keyboard focus and click. Preserve a table alternative, visible focus, readable labels and empty/error messages.

States to design before implementation

First visit: prompt for project and iteration with a clear primary action; no save requirement. Loading: retain the applied filters and show a progress state. No matches: offer reset or a wider range. No history: explain that the iteration has never run. Fetch failure: keep prior data with its timestamp, show an error and Retry. Permission loss: explain the unavailable selection without exposing its results.

What works in these files

View navigation, local named saved view, date filtering, project-dependent suggestions, advanced status/environment filters, suite search, sort, CSV export, details dialogs, board selection and clickable daily history. The files work offline without external assets or libraries.

The iteration picker uses a native datalist as a lightweight stand-in for a searchable hierarchy. Menu items outside the report are contextual labels. Full board editing, server requests, live refresh, permission enforcement and links to real execution records are implementation work.

The table contains 12 illustrative runs. The board contains a separate 30-day illustrative dataset and uses daily aggregation; their totals are not intended to reconcile. Local saved views support one preset per mockup. All demonstration results are invented.
